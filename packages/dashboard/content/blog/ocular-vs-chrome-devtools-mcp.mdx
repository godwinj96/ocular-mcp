## The default, and the one case it can’t cover

[chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp) is Google’s own MCP
server for Chrome. Free, official, 51.6k GitHub stars, 1.43 million npm installs a week. If your
agent has touched a browser recently there’s a good chance this is what it reached for, and there’s
a good reason for that. It is the default, and the default is usually right.

This is about the one case where it structurally isn’t.

[Google’s launch post](https://developer.chrome.com/blog/chrome-devtools-mcp) frames the problem it
solves plainly: agents “are not able to see what the code they generate actually does when it runs
in the browser.” That’s true. It is also half the problem. Most of the web isn’t code your agent
generated.

## Where the two actually differ

chrome-devtools-mcp’s own documentation is direct about its shape. It drives **your own local
Chrome**, “designed to run on the same machine as the browser.” Remote Chrome appears in its docs as
a possible future direction, not a feature. That isn’t a limitation the project is hiding. It is
what a debugging tool for the browser you already have open is supposed to be.

It does mean the boundary is real. Point it at a page that isn’t running on your machine and you are
back to describing that page to your agent instead of showing it.

That boundary is where Ocular starts. Same MCP connection, same read-only posture, rendering pages
your local browser was never going to reach, alongside your dev server. Base tier clears most of the
open web. Most, not all.

|                  | chrome-devtools-mcp             | Ocular                   |
| ---------------- | ------------------------------- | ------------------------ |
| Coverage         | Local Chrome only               | Localhost + the open web |
| Acts on the page | Yes: clicks, types, fills forms | No, by design            |
| Tools            | ~58                             | 4, all read-only         |
| Made by          | Google                          | One developer            |
| Price            | Free                            | From $2.50/mo            |

## Two jobs, not two tiers

These are different tools for different jobs, and the comparison only makes sense once that is on
the table.

chrome-devtools-mcp gives an agent a driving seat. Ten of its tools handle input alone, plus
navigation, waiting, Lighthouse, traces, and the console and network panels. It can run an
interaction end to end.

Ocular gives it a viewport. Four tools, none of which touch the page. It renders what is there and
hands back the pixels and the element tree, annotated with what is in view and what sits below the
fold. If the job is “click through this checkout flow,” this is the wrong tool and never tried to be
the right one.

Read-only isn’t fifty-four tools short. It is built for the moment your agent needs eyes on
something rather than hands on it, and a driving seat left open on a page you were never going to
operate is not a feature you asked for.

There is a real tradeoff underneath that, running both directions. A tool that can act on a live
page can also modify one, which is a property of what a driving seat is for and worth knowing when
you pick. That is not a claim about which tool is safer to point at any given page. Whatever either
one renders still lands in your agent’s context.

## Setup, and what it costs to keep running

Both are a few lines in an MCP client config with nothing else to install. chrome-devtools-mcp
launches via `npx`. Ocular’s local worker does the same, then asks for a one-time sign-in, the way
any CLI tool authenticates once and remembers.

Price is where they part. chrome-devtools-mcp is free, with no ceiling to run into. Ocular is $2.50
a month: unmetered on localhost, because that is your own machine doing the work, and 40 renders a
day on the open web, because that half runs through infrastructure that isn’t free.

So the question was never which one is better. It is whether you hit the second half of the job
often enough to care.

## Where this earns its keep

Three ordinary moments, all of which end the same way today. Your agent asks you to go look, or it
works from your description of what it can’t see.

**A competitor built something and you want to know how.** Their page runs on their machine, not
yours. Nothing local opens it for your agent.

**A teammate drops a staging link in Slack.** It sits behind a URL your local Chrome profile has
never seen.

**Your agent needs the current documentation**, not the version that was in its training data the
day it shipped.

None of these are exotic. They are the ordinary shape of a working week, and every one of them is a
point where a localhost-bound tool runs out of road.

## Which one you want

chrome-devtools-mcp is still the right tool for driving a page you can already reach. Ocular is for
the page your agent can’t drive to, and for your dev server, from one connection. Four tools that
only look.
